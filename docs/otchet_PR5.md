## 3. Доработка индивидуального проекта

### 3.1. Проект и приложения

Django-проект `guideservice`: `manage.py` лежит в корне репозитория
`guide_service` рядом с консольным приложением, настройки —
в `guideservice/settings.py`, корневая маршрутизация —
в `guideservice/urls.py`. Созданы пять приложений, все зарегистрированы
в `INSTALLED_APPS`:

| Приложение | Зачем нужно |
| --- | --- |
| `homepage` | главная страница, общий каркас HTML-страниц, страница 404 |
| `guides` | список гидов и карточка гида |
| `routes` | список маршрутов и карточка маршрута |
| `excursions` | список экскурсий и карточка экскурсии |
| `schedules` | расписание занятий и карточка занятия |

### 3.2. Страницы и адреса

| Страница | URL | view-функция |
| --- | --- | --- |
| Главная | `/` | `homepage.views.index` |
| Гиды | `/guides/` | `guides.views.guides` |
| Карточка гида | `/guides/<int:guide_id>/` | `guides.views.guide_detail` |
| Маршруты | `/routes/` | `routes.views.routes` |
| Карточка маршрута | `/routes/<int:route_id>/` | `routes.views.route_detail` |
| Экскурсии | `/excursions/` | `excursions.views.excursions` |
| Карточка экскурсии | `/excursions/<int:excursion_id>/` | `excursions.views.excursion_detail` |
| Расписание | `/schedules/` | `schedules.views.schedules` |
| Карточка занятия | `/schedules/<int:schedule_id>/` | `schedules.views.schedule_detail` |
| Страница 404 | любой несуществующий адрес | `homepage.views.page_not_found` |

### 3.3. Краткое описание выполненной работы

Маршрутизация двухуровневая: `guideservice/urls.py` через `include()`
подключает `urls.py` приложений, где описаны конкретные адреса
с конвертерами `<int:...>` и именем `name`. View-функции не дублируют
логику ПР3: берут данные через `storage.load_guides()` и
`storage.load_all()`, находят объект (`get_guide()`, `get_route()`,
`get_excursion()`, `get_schedule()`), а при отсутствии id возвращают 404
вместо исключения `NotFoundError`.

Вёрстка собирается в Python-коде: `page()` в `homepage/views.py`
подключает Bootstrap 5.3 по CDN, выводит навигацию по четырём разделам
и оборачивает содержимое в контейнер; используются `list-group`, `card`,
`badge`, `btn`. Своя 404 подключена через `handler404` в корневом
`urls.py` и включается при `DEBUG = False` (режим переключается
переменной окружения `DJANGO_DEBUG`, сервер запускается
с ключом `--insecure`, чтобы он отдавал стили при выключенной отладке).

### 3.4. Проблемы при подготовке проекта к Django

* Модуль `statistics.py` в корне перекрывал стандартный модуль Python,
  и Django не запускался с ошибкой
  `AttributeError: module 'statistics' has no attribute 'pstdev'`.
  Файл переименован в `reports.py`, ссылки обновлены.
* В консольной части вызывались неимпортированная `create_route`
  и `add_excursion` с неверными аргументами вместо `create_excursion`,
  плюс были замечания flake8. Всё исправлено отдельным коммитом.

### 3.5. Проверки

`python manage.py check` — без замечаний. `pytest -v` — 30 тестов
проходят. `flake8 . --extend-exclude=.venv` — без замечаний. Все девять
адресов проверены на запущенном сервере и отдают код 200, несуществующие
id и адреса — 404.

Число тестов указано на момент сдачи ПР5. В следующих работах добавились
проверки шаблонов и базы данных, поэтому сейчас `pytest` находит 46 тестов.

## 5. Вывод

В ПР5 консольное приложение стало веб-приложением: запрос идёт от URL
через `urls.py` и view-функцию до готовой HTML-страницы, а данные
остались объектами ПР3. Я понял, зачем нужны `settings.py`, корневой
`urls.py` и `manage.py`, как работают конвертеры пути и почему ошибку 404
лучше обрабатывать своей страницей. Веб-слой добавляется к готовой
модели, не переписывая её, — дальше шаблоны Django и Django ORM.
