## 4. Доработка индивидуального проекта

### 4.1. Модели и поля

Модели лежат в `models.py` своих приложений; классы предметной области из
корневого `models.py` остались для консольной части.

| Модель | Приложение | Поля |
| --- | --- | --- |
| `Guide` | `guides` | `name` CharField(200), `specialization` CharField(100), `languages` CharField(200), `experience_years` PositiveIntegerField, `rating` DecimalField(3,1), `is_active` BooleanField |
| `Route` | `routes` | `name` CharField(200), `description` TextField, `duration_hours` DecimalField(4,1), `distance_km` DecimalField(6,1), `difficulty` с `choices`, `required_languages` CharField(200), `is_active` BooleanField |
| `Excursion` | `excursions` | `title` CharField(200), `route` ForeignKey, `kind` с `choices` («обычная» и «семейная»), `base_price` DecimalField(8,2), `max_participants` PositiveIntegerField, `min_age` PositiveIntegerField, `languages` CharField(200), `is_active` BooleanField |
| `Schedule` | `schedules` | `excursion` ForeignKey, `guide` ForeignKey, `date` DateField, `start_time` TimeField, `booked` PositiveIntegerField, `status` с `choices`, `note` TextField |

У моделей заданы `verbose_name`, `Meta.ordering`, метод `__str__` и
вычисляемые свойства: `languages_list` у гида, `duration_hours` и
`is_family` у экскурсии, `free_seats`, `revenue`, `fill_percent` у занятия.
Логика предметной области осталась в моделях: `knows_languages()` проверяет
языки, `is_suitable_for()` — вместимость, `total_price()` считает стоимость
со скидкой группе от шести человек и с детской скидкой в семейной
экскурсии, `cancel()` и `mark_done()` меняют статус занятия.

### 4.2. Связи между моделями

Настроены три связи «многие к одному»:

| Связь | Поле | `on_delete` | `related_name` |
| --- | --- | --- | --- |
| маршрут → экскурсии | `Excursion.route` | `PROTECT` | `excursions` |
| экскурсия → занятия | `Schedule.excursion` | `PROTECT` | `schedules` |
| гид → занятия | `Schedule.guide` | `PROTECT` | `schedules` |

`PROTECT` выбран намеренно: нельзя удалить маршрут, по которому уже есть
экскурсии, и нельзя удалить гида или экскурсию, на которые ссылаются
занятия. `related_name` даёт обратные выборки: `route.excursions`,
`excursion.schedules`, `guide.schedules`.

У занятия есть ограничение `CheckConstraint` на неотрицательное число
броней (`schedule_booked_not_negative`) и индекс по дате
(`schedule_date_idx`).

### 4.3. Миграции

Командой `python manage.py makemigrations` созданы, а `migrate` применены
четыре начальные миграции — по одной в каждом приложении с моделями:

| Приложение | Миграции |
| --- | --- |
| `guides` | `0001_initial` |
| `routes` | `0001_initial` |
| `excursions` | `0001_initial` |
| `schedules` | `0001_initial` |

Каждая миграция создаёт таблицу модели с полями, связями, ограничением
и индексом. Файлы миграций хранятся в репозитории: по ним структура базы
воспроизводится в любом окружении командой `migrate`.

### 4.4. Стратегия перехода и перенос данных

Выбран вариант 2: исходная база ПР7 `data/guideservice.sqlite` не
изменяется и остаётся источником, а Django работает со своей базой
`db.sqlite3` из `settings.DATABASES`. Так перенос можно повторить и
сравнить результат, не рискуя данными предыдущей работы.

Перенос выполняет скрипт `db/import_orm.py` (запуск
`python -m db.import_orm`): читает таблицы ПР7 через `sqlite3`, проверяет
внешние ключи, очищает целевые таблицы в порядке от зависимых к основным
и создаёт объекты моделей методом `bulk_create()` с теми же `id` — поэтому
связи сохраняются. Порядок вставки: маршруты и гиды, затем экскурсии,
затем занятия. Вся запись идёт внутри `transaction.atomic()`: при ошибке
база остаётся в прежнем состоянии. Перенесено 6 гидов, 5 маршрутов,
5 экскурсий и 8 занятий.

### 4.5. Операции ORM и представления

Представления больше не обращаются к `sqlite3` напрямую — они работают с
моделями.

| Страница | Что используется |
| --- | --- |
| списки гидов, маршрутов, экскурсий | `filter()`, `icontains`, `order_by()`, `annotate(Count(...))`, `select_related()`, `values_list()` |
| свободные гиды на дату | `filter(is_active=True)`, набор занятых `filter(date=..., status__in=...)`, затем `exclude(schedules__in=busy)` |
| карточки объектов | `get()`, `select_related()`, обработка `DoesNotExist` → страница 404, обратные связи `guide.schedules` |
| расписание | `Q`-объекты для поиска, фильтры по статусу, гиду и периоду, сортировка по пяти наборам полей, `Paginator` по пять занятий |
| статистика | `aggregate()` с `Count` и `Sum`, `annotate()` с `F()`, `Cast` и `Round` |
| активные занятия | `exclude(status="отменена")` |

Фильтры и сортировка передаются в адресе (`?q=`, `?status=`, `?guide=`,
`?date_from=`, `?date_to=`, `?sort=`) и сохраняются при переходе между
страницами: в ссылки пагинации подставляется строка параметров без номера
страницы.

При переходе нашлись две особенности:

* `exclude()` с двумя условиями по одной связи проверяет их отдельными
  подзапросами и исключает больше, чем нужно. Поэтому занятые гиды
  выбираются в два шага: сначала набор занятий на дату, затем
  `exclude(schedules__in=busy)`;
* в SQLite оператор `LIKE`, на котором основан `icontains`, не учитывает
  регистр для кириллицы: поиск по имени находит записи в том же регистре,
  что и в данных.

В ПР9 проект перешёл от ручных SQL-запросов к Django ORM: структура базы
теперь описана моделями и управляется миграциями, связи заданы внешними
ключами, а данные перенесены из базы ПР7 с сохранением идентификаторов и
связей. Представления стали короче и читаемее: вместо текста SQL в них
остались `filter()`, `exclude()`, `annotate()` и `aggregate()`, а расчёты и
правила предметной области живут в моделях. Прямой SQL из ПР7 сохранён как
предыдущая реализация и продолжает использоваться в консольной части, при
этом страницы и сценарии ПР5–ПР7 работают без изменений.
