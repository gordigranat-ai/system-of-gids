## 4. Доработка индивидуального проекта

### 4.1. Проект и приложения

Django-проект называется `guideservice`: `manage.py` лежит в корне
репозитория `guide_service` рядом с консольным приложением, настройки —
в `guideservice/settings.py`, корневая маршрутизация — в
`guideservice/urls.py`. Созданы пять приложений, все зарегистрированы в
`INSTALLED_APPS`:

| Приложение | Зачем нужно |
| --- | --- |
| `homepage` | главная страница, общий каркас HTML-страниц, страница 404 |
| `guides` | список гидов и карточка гида |
| `routes` | список маршрутов и карточка маршрута |
| `excursions` | список экскурсий и карточка экскурсии |
| `schedules` | расписание занятий и карточка занятия |

Отдельного приложения для пользователей нет: Django уже предоставляет
встроенную модель `User` в `django.contrib.auth`.

### 4.2. Маршрутизация и страницы

Маршрутизация двухуровневая: `guideservice/urls.py` через `include()`
подключает `urls.py` приложений, где описаны конкретные адреса с
конвертерами `<int:...>` и именем маршрута `name`.

| Страница | URL | view-функция |
| --- | --- | --- |
| Главная | `/` | `homepage.views.index` |
| Гиды | `/guides/` | `guides.views.guides` |
| Карточка гида | `/guides/<int:guide_id>/` | `guides.views.guide_detail` |
| Маршруты | `/routes/` | `routes.views.routes` |
| Карточка маршрута | `/routes/<int:route_id>/` | `routes.views.route_detail` |
| Экскурсии | `/excursions/` | `excursions.views.excursions` |
| Карточка экскурсии | `/excursions/<int:excursion_id>/` | `excursions.views.excursion_detail` |
| Расписание | `/schedules/` | `schedules.views.schedules` |
| Карточка занятия | `/schedules/<int:schedule_id>/` | `schedules.views.schedule_detail` |
| Страница 404 | любой несуществующий адрес | `homepage.views.page_not_found` |

### 4.3. View-функции и данные проекта ПР3

View-функции не дублируют логику ПР3: данные берутся через
`storage.load_guides()` и `storage.load_all()`, объект находится функциями
`get_guide()`, `get_route()`, `get_excursion()`, `get_schedule()`. Если
объекта с таким id нет, возвращается ответ с кодом 404 вместо исключения
`NotFoundError`. Связанные объекты выводятся через атрибуты: например,
страница занятия показывает `schedule.excursion.title` и
`schedule.guide.name`.

### 4.4. Оформление и страница 404

Вёрстка собирается в Python-коде: функция `page()` в `homepage/views.py`
подключает Bootstrap 5.3 по CDN, выводит навигацию по четырём разделам и
оборачивает содержимое в контейнер; используются классы `list-group`,
`card`, `badge`, `btn`. Собственная страница 404 подключена через
`handler404` в корневом `urls.py` и включается при `DEBUG = False`; режим
переключается переменной окружения `DJANGO_DEBUG`.

### 4.5. Проблемы при подготовке проекта к Django

* Модуль `statistics.py` в корне перекрывал стандартный модуль Python, и
  Django не запускался с ошибкой
  `AttributeError: module 'statistics' has no attribute 'pstdev'`. Файл
  переименован в `reports.py`, ссылки обновлены.
* В консольной части вызывались неимпортированная `create_route` и
  `add_excursion` с аргументами от `create_excursion`, плюс были замечания
  flake8. Всё исправлено отдельным коммитом до начала работы над веб-частью.

### 4.6. README и тесты

В `README.md` описаны назначение проекта, структура Django-проекта, таблица
страниц и view-функций, оформление, запуск и текущее состояние. В каталог
`tests/` добавлены тесты веб-интерфейса: каждая страница открывается,

## 8. Вывод

В ПР5 консольное приложение стало веб-приложением: запрос идёт от URL через
`urls.py` и view-функцию до готовой HTML-страницы, а данные остались
объектами ПР3. Я понял, зачем нужны `settings.py`, корневой `urls.py` и
`manage.py`, как работают конвертеры пути и почему ошибку 404 лучше
обрабатывать своей страницей. Веб-слой добавляется к готовой модели, не
переписывая её, — дальше шаблоны Django и база данных.
