# Сервис управления туристическими гидами

Мой индивидуальный проект. Начинался как консольная программа для
экскурсионного бюро, а в ПР5 у него появился веб-интерфейс на Django:
гиды, маршруты, экскурсии и расписание доступны в браузере. В ПР6
веб-часть переведена на Django-шаблоны, в ПР7 данные проекта переехали
в базу данных SQLite, в ПР9 работа с базой идёт через Django ORM,
а в ПР10 добавлены административная панель и панель анализа запросов.

Готовы ПР1, ПР2, ПР3, ПР5, ПР6, ПР7, ПР9 и ПР10.

## Что умеет

* гиды: список, поиск, отбор по языку и специализации, сортировка,
  добавление, удаление;
* маршруты: поиск, отбор по сложности и длительности, сортировка,
  добавление, удаление;
* экскурсии: поиск, отбор по цене и маршруту, расчёт стоимости со скидками;
* расписание: занятия на дату, по гиду и за период, добавление с проверкой
  занятости гида, бронирование и отмена мест, отмена занятия;
* статистика: загрузка гидов, популярность маршрутов, выручка, заполняемость
  занятий;
* данные сохраняются в JSON и загружаются при запуске;
* **в ПР5 добавился веб-интерфейс**: страницы гидов, маршрутов, экскурсий
  и расписания, а также собственная страница 404;
* **в ПР6 веб-часть переведена на шаблоны**: базовый шаблон с наследованием,
  включаемые части, циклы и условия, фильтры, именованные URL и собственные
  статические файлы;
* **в ПР7 появилась база данных**: таблицы `guides`, `routes`, `excursions`
  и `schedules` в SQLite, перенос данных из JSON, SQL-запросы и страницы
  на их основе — поиск свободных гидов на дату и статистика;
* **в ПР9 данные переведены на Django ORM**: модели с полями и связями,
  миграции, перенос данных из базы ПР7, поиск, фильтры, сортировка
  и постраничный вывод на страницах;
* **в ПР10 появились административная панель и работа с QuerySet**:
  настройка списков, фильтров, поиска, встроенных форм и массовых действий,
  статусы через `TextChoices`, адреса маршрутов по slug, менеджер
  `ScheduleQuerySet` и панель анализа SQL-запросов.

## Предметная область

Есть гиды и маршруты. По маршруту создаётся экскурсия с ценой и ограничением
по числу участников. Конкретное проведение экскурсии — занятие в расписании:
дата, время, гид, забронированные места.

Что проверяет программа:

* гид проводит только те экскурсии, языки которых знает;
* один гид не может вести два занятия в одно время;
* мест нельзя забронировать больше, чем вмещает экскурсия;
* отменённое занятие не удаляется, но время гида не занимает.

## Классы

Классы предметной области остались в корневом `models.py` и используются
и консольной частью, и веб-интерфейсом:

| Класс | Что хранит | Что умеет |
| --- | --- | --- |
| `Guide` | id, имя, специализация, языки, стаж, рейтинг | проверять языки, отдавать статус |
| `Route` | id, название, длительность, сложность, протяжённость | проверять длительность |
| `Excursion` | id, название, объект маршрута, цена, места | проверять вместимость, считать стоимость |
| `FamilyExcursion` | то же | то же, но детям цена со скидкой 50 % |
| `Schedule` | id, объекты экскурсии и гида, дата, время, брони | бронировать места, отменяться |

`FamilyExcursion` — наследник `Excursion`. Метод `total_price()` один,
а результат разный: для ребёнка семейная экскурсия считает половину цены.
Это полиморфизм.

Занятие ссылается на экскурсию и гида, а маршрут берётся через экскурсию,
поэтому работает `schedule.excursion.route.name`.

## Веб-часть на Django

### Проект и приложения

Django-проект называется `guideservice` и лежит в репозитории рядом
с консольным приложением: `manage.py` находится в корне, поэтому ничего
переносить не пришлось.

| Приложение | За что отвечает |
| --- | --- |
| `homepage` | главная страница, общий каркас страниц, страница 404 |
| `guides` | гиды |
| `routes` | маршруты |
| `excursions` | экскурсии |
| `schedules` | расписание занятий |

Приложения зарегистрированы в `INSTALLED_APPS` в `guideservice/settings.py`.
Для пользователей отдельного приложения нет: Django уже предоставляет
встроенную модель `User` в `django.contrib.auth`.

### Страницы и адреса

| Страница | URL | View-функция |
| --- | --- | --- |
| Главная | `/` | `homepage.views.index` |
| Гиды | `/guides/` | `guides.views.guides` |
| Карточка гида | `/guides/<int:guide_id>/` | `guides.views.guide_detail` |
| Маршруты | `/routes/` | `routes.views.routes` |
| Карточка маршрута | `/routes/<int:route_id>/` | `routes.views.route_detail` |
| Экскурсии | `/excursions/` | `excursions.views.excursions` |
| Карточка экскурсии | `/excursions/<int:excursion_id>/` | `excursions.views.excursion_detail` |
| Расписание | `/schedules/` | `schedules.views.schedules` |
| Карточка занятия | `/schedules/<int:schedule_id>/` | `schedules.views.schedule_detail` |
| Свободные гиды на дату | `/guides/available/?date=...` | `guides.views.available_guides` |
| Активные занятия | `/schedules/active/` | `schedules.views.active_schedules` |
| Статистика | `/schedules/statistics/` | `schedules.views.statistics` |
| Страница 404 | любой несуществующий адрес | `homepage.views.page_not_found` |

Маршруты распределены по двум уровням: `guideservice/urls.py` подключает
маршруты приложений через `include()`, а конкретные адреса описаны
в `urls.py` каждого приложения. У всех приложений задан `app_name`, поэтому
маршруты имеют пространства имён: `homepage:index`, `guides:list`,
`guides:detail`, `routes:list`, `excursions:detail`, `schedules:list`
и так далее. В шаблонах ссылки строятся по этим именам, а не по жёстко
записанным адресам.

### Как запрос превращается в страницу

1. браузер отправляет GET-запрос на адрес;
2. `guideservice/urls.py` выбирает приложение по префиксу;
3. `urls.py` приложения находит view-функцию и передаёт ей параметры из адреса;
4. view-функция берёт данные из базы (`db/repository.py`), находит нужный
   объект и собирает контекст;
5. `render()` подставляет контекст в шаблон, шаблон наследует `base.html`;
6. Django возвращает HTTP-ответ со страницей и кодом 200 или 404.

### Шаблоны

Веб-часть работает на Django Template Language. HTML в view-функциях
не собирается: view готовит контекст — словарь с данными — и вызывает
`render()`.

```
guideservice/templates/           шаблоны уровня проекта
├── base.html                     общий каркас всех страниц
├── not_found.html                общая страница «объект не найден»
└── includes/
    └── navigation.html           навигация, подключается через include

homepage/templates/homepage/      шаблоны приложений
guides/templates/guides/
routes/templates/routes/
excursions/templates/excursions/
schedules/templates/schedules/
```

Что используется:

| Возможность | Где применяется |
| --- | --- |
| наследование `{% extends %}` и блоки `{% block %}` | все страницы наследуют `base.html` и переопределяют `title` и `content` |
| include `{% include %}` | навигация, карточка гида, маршрута и экскурсии, статус занятия |
| контекст | `{"guides": ...}`, `{"guide": ..., "schedules": ...}` и другие |
| циклы `{% for %}` и `{% empty %}` | списки гидов, маршрутов, экскурсий, занятий |
| условия `{% if %}` | статус гида, статус занятия |
| именованные URL `{% url %}` | вся навигация и все внутренние ссылки |
| фильтры | `length`, `default`, `join`, `floatformat` |
| статические файлы `{% static %}` | собственный CSS, JavaScript и логотип |

Фильтры используются по назначению: `{{ guides|length }}` выводит количество
записей, `{{ guide.name|default:"Без имени" }}` подставляет текст, если
значение пустое, `{{ guide.languages|join:", " }}` склеивает список языков,
`{{ schedule.revenue|floatformat:0 }}` убирает дробную часть у суммы.
Фильтры только оформляют вывод и не заменяют расчёты: стоимость и скидки
по-прежнему считают методы классов.

### Оформление и статические файлы

Собственные статические файлы лежат в `homepage/static/homepage/`:

| Файл | Где используется |
| --- | --- |
| `css/style.css` | `base.html`, карточки гидов и маршрутов, статусы занятий |
| `js/main.js` | `base.html`: подставляет текущий год в подвал |
| `img/logo.png` | `base.html`: логотип в шапке сайта |

Подключение идёт через `{% load static %}` и `{% static '...' %}`.
Bootstrap 5.3 остаётся подключённым по CDN и отвечает за сетку и базовые
компоненты (`container`, `card`, `badge`, `btn`, `list-group`), а собственный
CSS проекта добавляет оформление: логотип, отступы, рамки карточек,
начертание статусов.

### Обработка ошибки 404

Собственная страница подключена через `handler404` в `guideservice/urls.py`.
Если объект с запрошенным id не найден, view-функция возвращает ответ
с кодом 404 и сообщением об ошибке.

По умолчанию отладка включена (`DEBUG = True`) — так встроенный сервер
раздаёт CSS и страницы выглядят оформленными. Собственная страница 404
показывается при выключенной отладке, и тогда сервер нужно запускать
с ключом `--insecure`, иначе стили не отдаются:

```
set DJANGO_DEBUG=0
python manage.py runserver --insecure
```

После проверки вернуть обычный режим:

```
set DJANGO_DEBUG=1
```

## База данных и SQL

Веб-часть берёт данные из SQLite-базы `data/guideservice.sqlite`. Схема
повторяет предметную модель ПР3 и лежит в `sql/schema.sql`:

| Таблица | Поля | Ключи |
| --- | --- | --- |
| `guides` | id, name, specialization, languages, experience_years, rating, is_active | id — первичный ключ |
| `routes` | id, name, description, duration_hours, distance_km, difficulty, required_languages, is_active | id — первичный ключ |
| `excursions` | id, title, route_id, kind, base_price, max_participants, min_age, languages, is_active | route_id → `routes.id` |
| `schedules` | id, excursion_id, guide_id, date, start_time, booked, status, note | excursion_id → `excursions.id`, guide_id → `guides.id` |

Связи такие же, как в модели: у маршрута несколько экскурсий, у экскурсии
несколько занятий, один гид может вести много занятий. Списки языков
хранятся одной строкой через запятую — так по ним можно отбирать
условием `LIKE`.

### Файлы для работы с базой

| Файл | Назначение |
| --- | --- |
| `sql/schema.sql` | команды создания таблиц и индексов |
| `sql/queries.sql` | одиннадцать запросов проекта с пояснениями |
| `db/database.py` | путь к базе, подключение, `row_factory`, выполнение схемы |
| `db/import_json.py` | перенос данных из JSON в SQLite |
| `db/repository.py` | выборка объектов для страниц: SQL и сборка классов |
| `data/guideservice.sqlite` | сама база |

### Как создать базу заново

```
python -c "from db.database import create_schema; create_schema()"
python -m db.import_json
```

Первая команда создаёт таблицы по `sql/schema.sql`, вторая переносит данные
из `data/*.json`. Повторный импорт очищает таблицы и заливает их заново,
поэтому команду можно запускать сколько угодно раз.

### Запросы

В `sql/queries.sql` одиннадцать запросов: `SELECT` и `WHERE`, соединение
четырёх таблиц, подзапрос `NOT IN`, `COUNT`, `GROUP BY`, `HAVING`,
`SUM` и `AVG`, `ORDER BY` вместе с `LIMIT`. Готовые запросы можно выполнить
в `sqlite3` как есть. В представлениях те же запросы выполняются
с заполнителем `?`, а значения передаются отдельным списком — данные
пользователя не попадают в текст SQL.

Например, поиск свободных гидов и подсчёт занятий по гидам:

```sql
SELECT g.id, g.name
FROM guides AS g
WHERE g.is_active = 1
  AND g.id NOT IN (
      SELECT s.guide_id FROM schedules AS s
      WHERE s.date = ? AND s.status <> 'отменена'
  )
ORDER BY g.name;

SELECT g.name, COUNT(s.id) AS schedules_count
FROM guides AS g
LEFT JOIN schedules AS s
       ON s.guide_id = g.id AND s.status <> 'отменена'
GROUP BY g.id, g.name
ORDER BY schedules_count DESC;
```

### Страницы на данных из базы

* `/guides/`, `/routes/`, `/excursions/`, `/schedules/` — списки и карточки
  собираются из объектов, которые `db/repository.py` строит по строкам базы,
  поэтому расчёты остаются в классах ПР3;
* `/guides/available/?date=2026-03-10` — свободные гиды на дату: форма
  отправляет дату методом GET, а запрос с `NOT IN` исключает занятых;
* `/schedules/active/` — занятия без отменённых;
* `/schedules/statistics/` — статистика: строки `sqlite3.Row` из запросов
  с `GROUP BY` передаются в шаблон и выводятся таблицами, поля читаются
  по именам (`item.schedules_count`).

## Модели Django и ORM (ПР9)

В ПР9 данные веб-части переведены с прямых SQL-запросов на Django ORM.

### Две базы и зачем они нужны

| Файл | Роль |
| --- | --- |
| `data/guideservice.sqlite` | исходная база ПР7: таблицы, созданные вручную через `sql/schema.sql`, источник данных для переноса |
| `db.sqlite3` | рабочая база Django из `settings.DATABASES`; в ней таблицы моделей, сессии и административная панель |

Исходная база не изменяется: она нужна, чтобы при необходимости повторить
перенос и сравнить результат.

### Модели

| Модель | Приложение | Поля | Связи |
| --- | --- | --- | --- |
| `Guide` | `guides` | имя, специализация, языки, стаж, рейтинг, работает ли | обратная связь `guide.schedules` |
| `Route` | `routes` | название, описание, длительность, протяжённость, сложность, языки | обратная связь `route.excursions` |
| `Excursion` | `excursions` | название, вид, цена, максимум участников, минимальный возраст, языки | `route` → `Route`, обратная связь `excursion.schedules` |
| `Schedule` | `schedules` | дата, время начала, забронировано мест, статус, примечание | `excursion` → `Excursion`, `guide` → `Guide` |

Связи «многие к одному» заданы через `ForeignKey` с `on_delete=PROTECT`
(нельзя удалить гида или маршрут, на которые ссылаются занятия)
и `related_name`; у моделей есть `Meta.ordering`, человекочитаемые
`verbose_name`, методы `__str__` и вычисляемые свойства (`free_seats`,
`revenue`, `fill_percent`, `duration_hours`). У занятия добавлено
ограничение `CheckConstraint` на неотрицательное число броней и индекс
по дате.

### Миграции и перенос данных

```
python manage.py makemigrations
python manage.py migrate
python manage.py showmigrations
```

Файлы миграций лежат в `<приложение>/migrations/0001_initial.py`
и хранятся в репозитории.

Данные переносятся из базы ПР7 отдельным скриптом:

```
python -m db.import_orm
```

Скрипт читает исходные таблицы через `sqlite3`, проверяет внешние ключи,
создаёт объекты моделей с теми же `id` (поэтому связи сохраняются)
и печатает количество записей. Порядок переноса — маршруты и гиды,
затем экскурсии, затем занятия.

### ORM в представлениях

| Страница | Что используется |
| --- | --- |
| списки гидов, маршрутов, экскурсий | `filter()`, `icontains`, `order_by()`, `annotate(Count(...))`, `select_related()` |
| свободные гиды на дату | `filter(is_active=True)`, подзапрос занятых, `exclude()`, разбор даты с сообщением об ошибке |
| карточки объектов | `get()`, обработка `DoesNotExist` → страница 404, `select_related()` |
| расписание | `Q`-объекты для поиска, фильтры по статусу, гиду и периоду, сортировка по пяти полям, `Paginator` |
| статистика | `aggregate()` для итогов и `annotate()` с `Count`, `Sum`, `Avg`, `Round` и `F()`-выражениями |
| активные занятия | `exclude(status="отменена")` |

Параметры фильтров и сортировки передаются в адресе (`?q=`, `?status=`,
`?guide=`, `?sort=`, `?date_from=`, `?date_to=`) и сохраняются при переходе
между страницами: в ссылках пагинации подставляется `querystring` без
номера страницы. Постраничный вывод — по пять занятий.

Две особенности, найденные при переходе:

* `exclude()` с двумя условиями по одной связи (например, «дата такая-то
  и статус такой-то») проверяет условия отдельными подзапросами
  и исключает больше, чем нужно. Поэтому занятые гиды выбираются так:
  сначала набор занятий, затем `exclude(schedules__in=busy)`;
* в SQLite оператор `LIKE`, на котором основан `icontains`, не учитывает
  регистр для кириллицы: поиск по имени работает для того же регистра,
  что и в данных. Для латиницы ограничения нет.

## Административная панель и QuerySet (ПР10)

### Статусы через TextChoices

Статус занятия описан классом `ScheduleStatus(models.TextChoices)`:
в базе хранятся короткие коды `active`, `completed`, `cancelled`,
а в интерфейсе показываются подписи «запланирована», «проведена»,
«отменена» через `get_status_display()`. Миграция
`schedules/0002_status_textchoices` переводит старые русские значения
в коды, поэтому существующие записи не теряются.

### Человекочитаемый адрес маршрута

У модели `Route` появилось поле `slug` и метод `get_absolute_url()`.
Slug собирается из названия транслитерацией (`Исторический центр` →
`istoricheskiy-tsentr`), уникальность обеспечивается в `save()`.
Карточка маршрута открывается по адресу `/routes/<slug>/`, а миграция
`routes/0002_route_slug` заполнила slug у уже существующих маршрутов.

### Менеджер занятий

`Schedule.objects` — это `ScheduleQuerySet` с готовыми выборками:
`with_related()`, `active()`, `completed()`, `cancelled()`, `for_guide()`,
`on_date()`, `busy_guides()` и `totals()`. Представления используют их
вместо повторяющихся `filter()` и `select_related()`.

### Настройки административной панели

| Модель | Что настроено |
| --- | --- |
| `Guide` | столбцы с числом занятий (`annotate`), поиск по имени, специализации и языкам, фильтры, редактирование `is_active` прямо в списке, рейтинг только для чтения, встроенные занятия |
| `Route` | slug только для чтения, фильтр по сложности, поиск по названию и описанию, число экскурсий в списке, встроенные экскурсии |
| `Excursion` | связанный маршрут в списке (`list_select_related`), автодополнение маршрута, фильтры по виду и маршруту, встроенные занятия |
| `Schedule` | иерархия по датам (`date_hierarchy`), фильтры по статусу, дате, гиду и маршруту, поиск по экскурсии и гиду, редактирование `booked` и `status` в списке, вычисляемые «свободно мест» и «выручка» только для чтения, массовые действия «отметить проведёнными» и «отменить» |

Заголовки панели переопределены в `homepage/admin.py`: «Экскурсионное
бюро» вместо «Администрирование Django».

### Django Debug Toolbar

Панель анализа запросов подключена в `settings.py`
(`debug_toolbar` в `INSTALLED_APPS`, middleware, `INTERNAL_IPS`) и в
корневых маршрутах по адресу `/__debug__/`. Показывается только при
включённой отладке и только на страницах сайта: в админке она мешает,
поэтому условие вынесено в `guideservice/debug.py`. Панель SQL показывает
запросы страницы, время выполнения и количество обращений к базе.

### Контекстный процессор

`homepage/context_processors.counters` передаёт в каждый шаблон количество
гидов, маршрутов, экскурсий и занятий, а также текущую дату. Поэтому
подвал сайта показывает сводку без участия представлений.

### Скриншоты работы

В `docs/screens/` лежат снимки работающего приложения: список моделей
админки, список занятий с фильтрами и поиском, страница гида со
встроенными занятиями, страница маршрута, карточка маршрута по slug,
страница статистики и панель SQL в Django Debug Toolbar.

## Данные

Данные живут в двух местах, и это осознанно.

**JSON-файлы** в `data/` — исходные данные ПР1–ПР3 и источник для импорта.
Связанные объекты хранятся идентификаторами:

```json
{
  "id": 1,
  "excursion_id": 1,
  "guide_id": 1,
  "date": "2026-03-10",
  "start_time": "10:00",
  "booked": 8,
  "status": "запланирована"
}
```

При загрузке по `excursion_id` и `guide_id` находятся объекты, и занятие
получает на них ссылки. Если файла нет — программа начнёт с пустых списков,
если JSON испорчен — скажет об этом и продолжит работу. JSON используют
консольное приложение и `db/import_json.py`.

**База SQLite** `data/guideservice.sqlite` — исходная база ПР7. Таблицы
заполняются из JSON командой `python -m db.import_json`; после ПР9 она
служит источником для переноса в модели.

**База Django** `db.sqlite3` — рабочая база веб-части: таблицы моделей
ПР9, сессии и административная панель. Наполняется командой
`python -m db.import_orm`, которая читает исходную базу ПР7 и создаёт
объекты моделей с теми же идентификаторами.

## Запуск

Консольная версия:

```
python main.py
```

Или двойным щелчком по `run.bat`.

Веб-версия: нужен Python 3.11+ и виртуальное окружение.

```
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m db.import_json
.venv\Scripts\python.exe manage.py migrate
.venv\Scripts\python.exe -m db.import_orm
.venv\Scripts\python.exe manage.py runserver
```

После запуска открыть `http://127.0.0.1:8000/`.

Если окружение и база уже готовы, сайт поднимается одной командой:

```
.\.venv\Scripts\python.exe manage.py runserver
```

или двойным щелчком по `run_web.bat`.

Порядок подготовки баз:

1. `python -m db.import_json` пересоздаёт базу ПР7 `data/guideservice.sqlite`
   из JSON-файлов (нужно, только если исходная база потеряна);
2. `python manage.py migrate` создаёт таблицы Django-моделей, сессии
   и административную панель в `db.sqlite3`;
3. `python -m db.import_orm` переносит данные из базы ПР7 в модели.

Повторный `python -m db.import_orm` безопасен: таблицы моделей очищаются
и заполняются заново с теми же идентификаторами.

Административная панель доступна по адресу `http://127.0.0.1:8000/admin/`.
Для входа нужен суперпользователь — создайте его один раз:

```
.\.venv\Scripts\python.exe manage.py createsuperuser
```

Python вызывается по полному пути `.venv\Scripts\python.exe`, потому что
на этой машине выполнение скриптов PowerShell ограничено и активация
окружения через `Activate.ps1` не срабатывает. При желании можно включить
её для текущего окна:

```
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

## Тесты

```
.\.venv\Scripts\python.exe -m pytest
```

Django-модели тестируются через `pytest-django`: плагин создаёт отдельную
тестовую базу, поэтому реальные данные не затрагиваются. Тесты проверяют:

* модели и их методы: стоимость группы, скидки, свободные места, статусы;
* ORM-запросы: фильтры, `exclude`, `Q`, сортировку, `values`, `aggregate`,
  `annotate`, `select_related`, `Paginator` и обратные связи;
* страницы: поиск, фильтры, сортировку, пагинацию, 404 и обработку
  некорректных параметров;
* административную панель: вход, поиск, массовые действия и встроенные
  формы занятий;
* консольную часть (классы ПР3, JSON) и слой ПР7 (`sql/queries.sql`).
